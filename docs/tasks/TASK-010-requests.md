## Goal
«Самая важная часть» по формулировке самого Стаса. Каталог без работающей заявки —
просто справочник, денег с него нет.

## Что сделать
1. `POST /v1/requests` — приём. Обязателен `description` плюс телефон или email.
   Антиспам: honeypot-поле, rate limit по IP, минимальное время заполнения формы.
   Капчи в V0 нет.
2. Письмо оператору на каждую заявку (адрес в `.env`, по умолчанию `stanis.rum@gmail.com`).
   Отправка через очередь с ретраями: потерянная заявка — это потерянные деньги,
   а не просто пропущенное письмо.
3. `GET /v1/requests/public` — публичный список. **Не отдаёт `customer_name`,
   `customer_phone`, `customer_email`, `internal_note`** ни при каких условиях.
4. `POST /v1/requests/{id}/responses` — отклик поставщика («Я поставщик, хочу откликнуться»).
5. `POST /v1/companies/{slug}/claims` — «Я представитель компании»,
   типы `update | delete | verify | add_info`.
6. Экраны в панели: заявки со статусами (`new` → … → `completed`), подбор компаний
   в `request_companies`, смена статусов контактов, комментарии.
7. `GET /admin/stats/funnel` — воронка по `request_companies`:
   заявок → контактов → ответили → заинтересовались → дошли до клиента.
   Пункт 7 спеки: именно это через месяц даст реальные метрики бизнеса.

## Приёмка
- Тест: `GET /v1/requests/public` на заявке с заполненными ПД — в СЫРОМ ответе нет
  ни имени, ни телефона, ни email, ни внутренней заметки. Проверять текст ответа,
  а не типы: типы врут, если сериализация мимо них.
- Заявка создаётся при выключенном SMTP: письмо ложится в очередь, заявка в базе.
  Падение почты не должно терять заявку.
- Воронка на посеянных данных даёт правильные числа — сверить руками на 10 записях.

## Границы
Схему не трогать. Личных кабинетов и авторизации поставщиков нет — он просто
заполняет форму, дальше людей сводит оператор.
