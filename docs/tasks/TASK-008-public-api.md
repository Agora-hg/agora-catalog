## Goal
Всё из `docs/API.md`, раздел «Чтение каталога». Это то, чем живёт фронт.

## Что сделать
`apps/api`: `/v1/companies`, `/v1/companies/{slug}`, `/v1/categories`,
`/v1/categories/{slug}/companies`, `/v1/search`.

- Фильтры `category`, `city`, `verified`, `q`. Пагинация. Сортировка.
- Поиск — **строго по рецепту из `docs/API.md`, раздел «Поиск»**: FTS по `search_vector`
  ИЛИ `word_similarity` (`<%`) по `name`, `products_text`, `description`.
  Одного FTS недостаточно: русский стеммер даёт «печать» → `печа`, а «печатью» → `печат`,
  и запрос в именительном падеже не находит карточку. Это проверено на живом движке,
  не предположение — не «упрощай» до одного условия.
  Оператор `%` (без `<`) не подходит: сравнивает строки целиком.
  Ни AI-поиска, ни Elastic в V0.
- Кэш ответов 5-15 минут, инвалидация при правке компании из панели.
- Ответы строго в формах из `docs/API.md`. Поля не добавлять и не переименовывать:
  на эти формы параллельно пишется фронт (TASK-012).

## Приёмка
- `is_deleted = 1`, `is_active = 0` и `status = 'inactive'` не появляются ни при одном
  наборе фильтров. Тест обязателен: заведи такие записи и проверь каждый эндпоинт.
- `description_raw` не утекает ни в одном ответе. Тест обязателен, по сырому JSON,
  а не по типам.
- `GET /v1/search?q=пакеты с логотипом` находит компанию, у которой это есть только
  в `products_tags`.
- `GET /v1/search?q=печать` находит компанию с тегом «С печатью». Это тот самый случай,
  который валится на чистом FTS — обязательный тест.
- `products_text` обязан заполняться всюду, где меняются `products_tags`
  (импортёр, панель): именно он попадает в поисковый вектор, сам массив — нет.
- `checked_at` отдаётся как сегодняшняя дата, `is_verified` — как есть в базе.
  Врать про ручную проверку нельзя: дата обновляется, флаг проверки — нет.
- Замер: `/v1/companies` с фильтром на 1000 компаний, время ответа в отчёте.
